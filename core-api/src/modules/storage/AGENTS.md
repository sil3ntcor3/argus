# Object storage and signed URLs

`StorageService` owns the S3-compatible object layer. It uses separate clients
for server operations and URL signing. This module does not own database tables.

- `BUCKET_ACCESS` is the classification used by the generic presign routes.
  The upload route requires a platform admin and rejects private buckets.
  The download route requires a session, then applies bucket authorization.
- `job-results`, `reports`, and `artifacts` are private. Domain services
  authorize the caller before issuing a signed URL; the low-level helpers
  do not check the caller or bucket class. Verify any pre-existing artifacts
  bucket denies anonymous access before enabling writers. Startup does not
  replace operator-managed private bucket policies.
- Tenant reads resolve workspace ownership by object key. Screenshots resolve
  through asset services and targets; the `nuclei-templates` bucket
  resolves through the template row. Screenshots with the same asset value
  can share an object key, so membership of any owning workspace can grant
  a read. A tenant object with no owner cannot be downloaded generically.
- The object store can allow anonymous GET for `system` and `cached-static`.
  `cached-static` authentication applies to the generic API route. That route
  issues signed URLs; `getClientUrlForPath` can return unsigned URLs after the
  policy is verified. The `default` bucket is blocked for generic reads.
- An unset `STORAGE_URL_BASE` uses the same-origin proxy at `/api/storage`.
  An explicitly empty value uses absolute URLs, with `S3_PUBLIC_ENDPOINT`
  controlling the browser-facing endpoint. Keep the signing host and proxy
  configuration in sync.
- Presigned URL TTLs are clamped. At TTLs of two hours or more the signing
  timestamp is rounded down to the hour for repeatable URLs. Preserve the
  threshold when changing expiration or caching.
- Upload and download presigning validate object keys. Download file names
  go through `attachmentDisposition` to preserve the header syntax. Generic
  keys are generated by the service rather than accepted from upload clients.

Use the storage controller and service specs for authorization and signing
changes. Run `task api:test:e2e:one SPEC=test/storage-read-authz.e2e-spec.ts`
against local Docker when changing tenant bucket reads.
